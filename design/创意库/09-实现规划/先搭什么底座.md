# 先搭什么底座

这些是可尝试的实现路线，还没有经过试玩验证。用二维俯视、网格地图和少量房间就能检验大部分核心判断；真的需要透视错觉或身体尺度的条目，再单独做三维原型。没有必要现在就把全部点子塞进同一个项目。

如果从零开始，可以用 Godot 4 做二维原型；熟悉 Unity 的人直接用 Unity 也完全合理。下面刻意把规则与引擎分开写，避免为了某个功能过早绑定工具。

## 先分开三件容易混在一起的事

**现实是什么。**门是否开着、房间是什么版本、谁在哪、哪个机关正在工作。这份状态决定碰撞与实际结果。

**角色知道什么。**玩家、追逐者、同伴各有自己的记录。怪物不能直接从现实状态里读取从未观察过的玩家位置。

**界面显示什么。**眼前能看见的范围、地图的旧记忆、猜测、声源提示属于不同图层。地图可以过时，但显示层不能偷偷改变实际碰撞。

例如，桥被洪水冲断之后，现实中先移除桥的连接；玩家旧地图仍保留桥；只有再次观察，地图才写入新的样子。追逐者是否知道断桥，则取决于它自己的观察。

## 一套够用的数据

| 记录 | 最初需要哪些字段 | 用处 |
| --- | --- | --- |
| 地点 Place | 稳定编号、区域、版本、可站立点、标签 | 换外观之后仍知道它是哪个地方 |
| 连接 Link | 两端、开放条件、方向、允许通过的身体类型 | 门、传送、身份路、折纸路线共用 |
| 观察 Observation | 谁看见、看见什么、何时、依据、确定程度 | 旧地图、证词、敌人知识分开 |
| 事件 Event | 稳定编号、发生时刻、参与者、参数、是否已应用 | 存档、因果、回放与剧情追溯 |
| 承诺 Promise | 双方、内容、截止条件、延期与补救方式 | 关系不是只有好感值 |
| 线索 Evidence | 来源、可支持的判断、反证、发现条件 | 推理可验证，也允许悬而未决 |
| 人物 Actor | 位置、当前目标、知识、边界、日程 | 同伴与居民有自己的行为 |

不用一开始就写通用编辑器。先用可读的数据文件和手工场景验证，确认会反复改哪些字段，再做编辑面板。

## 第一版探索底座

移动先使用固定网格或简单碰撞体。视野可用网格阴影投射，或向障碍边界做射线检测；记住遮挡，不要只有一个能透墙的圆。显示时把“当前可见”“以前看见”“还不知道”分开。

地图为每个格子保存最后观察到的内容与时刻，远处的改变不立即覆盖记忆。交互统一为观察、使用、放置、交给、标记几个动作。进入新区域时保存进度，读档后恢复到同一个规则状态。

先做六个房间：一个分岔、一个环路、一个可靠地标、一条会变化的连接、一处休息点和一个明确目标。它们足够检验信息与路线，不需要先造“大地图”。

## 事件怎样驱动世界

```text
玩家做动作
  → 检查条件与成本
  → 产生一次有编号的事件
  → 更新现实状态
  → 更新真正观察到它的角色知识
  → 刷新画面、地图与声音
  → 在安全点保存
```

世界变化按明确顺序处理：连接与碰撞先定下来，角色再找路，最后刷新反馈。不能一帧里地图说门开了、碰撞却仍然挡着人。

会跨多个区域发生的变化，先计算全部新状态，通过合法性检查后一次提交。失败则整次撤销，避免只改了一半。读档和回放应识别事件编号，不把奖励、人口迁移或物品转移重复执行。

## 时间机制别从“模拟所有未来”开始

可回溯区域保存一个起点快照，再记录之后的动作。物理回放容易积累误差，原型优先使用离散位置、确定的机关和可复现的随机种子。

历史、当下和预览要分开：预览只显示“在目前条件下会发生什么”。如果玩家改变条件，预览可以失效，但必须明显取消；不能先把条件预测包装成必然预言，再随意反悔。

涉及过去影响现在时，用手工设计的因果表开始。比如“树种在 A→现在 A 有树根”，不从全世界任意改写开始。每条因果都要标出是否可撤销、哪些人物会记得、玩家所站位置如何保持安全。

## 动态空间的安全边界

房间连接可变化，房间本身先保持稳定。改变门的目的地，比连续扭曲整张三维地图更容易做清楚。切换前检查角色是否站在门槛、是否把关键物品隔离、是否留下可恢复的路线。

最初的可解性检查可以是图搜索：玩家所在位置能否回到避难所，或能否通过已拥有的能力抵达目标。带时序、身份和物品条件的谜题需要把这些状态也纳入搜索，不能只检查几何连通就宣布可解。

## 人物不必依赖联网生成

同伴使用手写的目标、有限状态和情境对白就能表现出性格。先让他会等待、请求、拒绝、绕路和解释理由，再考虑更复杂的规划。

共绘地图的笔迹可由预写线段动画、固定回应与条件分支产生。允许玩家用有限符号、圈点、位置和短语交流，避免承诺能理解任何自由输入。所有核心内容保持离线可用。

## 存档至少保存这些

保存现实状态、各方观察、已经发生的事件、人物承诺、未完成因果和玩家标注。仅保存位置与背包会让这类游戏读档后像换了一个世界。

为存档加版本号；稳定编号与显示名称分离。设计调整之后，可以明确迁移旧存档，或声明某个原型版本不能继承，别默默丢掉人物关系。

## 原型做完先问什么

玩家能否说清自己刚刚依据什么做决定？失败后能否提出一个不同做法？理解之后能否更顺畅地行动？如果不能，先修反馈和规则，不急着扩大内容量。

文档中的“先做一小段”都是建议的验证场景，不代表已经开发、运行或通过测试。难度与成本也需按实际团队、美术目标和工具经验重新评估。
